Battlevive Bot stores synchronized Battlevive data and per-server Discord state in PostgreSQL.

## Core tables

### `users`

Stores only the active authoritative Battlevive user snapshot. `discord_id` remains a compatibility cache for active users and older bot images.

Important rule: `discord_id` is bot-owned local state and must never be overwritten from the untrusted upstream field. A successful users response is authoritative, including an empty response: absent users are removed atomically, ratings cascade, lobby creator and captain references become null, and roster arrays are scrubbed. Fetch, parse, validation, or transaction failures do not delete users.

### `user_discord_links`

Canonical recovery mapping from upstream user UUID to a unique Discord ID. It deliberately has no foreign key to `users`, so a same-UUID account can recover its link after disappearing and later returning. A retained link alone grants no membership, rank command access, leaderboard entry, or role. New links are dual-written to this table and the active-user cache under a Discord-ID advisory lock.

### `season_ratings`

Stores one rating row per user and season.

Unique key:

```text
(user_id, season_year, season_number)
```

### `lobbies`

Stores the authoritative 30-second lobby snapshot, including lobby metadata, status, result state, match-link components, map selection, and tournament fields.

### `lobby_rosters`

Stores one row for each `(lobby_id, team)` pair.

It contains:

- captain ID;
- ordered roster user IDs;
- ordered final picks;
- ordered final bans;
- final-draft persistence timestamp.

Map-ban actions are deliberately excluded from stored champion bans.

## Discord server state

### `guild_config`

Stores one independent configuration row per Discord server, including:

- leaderboard channel and limit;
- debug-export flag;
- active-lobby channel;
- new-lobby notification role;
- Website Moderator role;
- active-lobby baseline state.
- rank cooldown from 0 through 3600 seconds (default 20).

### `guild_command_channels`

Stores one `allow` or `block` classification per guild/channel pair. Reclassification replaces the old rule, and rows cascade with guild configuration.

### `guild_created_roles`

Records only notification roles actually created by the bot after migration 09, keyed by guild and purpose. Only these exact roles are eligible for automatic deletion. Same-named legacy or custom roles are never backfilled or adopted.

### `leaderboard_slots`

Stores leaderboard message mappings, rendered-content fingerprints, season metadata, and cached user slots.

Complete PNG files are stored on disk rather than inside PostgreSQL.

### `active_lobby_posts`

Stores the current Discord message mapping and durable notification history for each lobby and guild.

Clearing a message mapping does not erase first-seen or handled-notification history. This prevents normal recovery operations from intentionally repeating role pings.

### `active_lobby_empty_posts`

Tracks the single per-guild empty-state message.

### `active_lobby_obsolete_posts`

Queues old Discord message references for cleanup. Failed deletions remain queued and are retried.

When a lobby disappears from the authoritative upstream list, live Discord references are copied here before the local lobby and roster rows are deleted.

## Write order

Synchronize the authoritative `users` snapshot before `lobbies`, `lobby_rosters`, and `season_ratings`, because those records reference active local users. Ratings and lobby references absent from the same users response are sanitized before dependent writes.

Reject roster user IDs that are not already present locally before writing roster arrays.
